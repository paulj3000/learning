Status: Development Complete on `feature/mvp-realm-asset-support` (from `main` `41ee7320`); not
merged, not owner-accepted. Part of the November 26 MVP Playability Stabilization cycle. This is
an audit plus one narrow fix; no Asset Library redesign, no new or third-party assets, no upload,

## 1. Realm thumbnail availability (PR #104)

How the redesigned Realms page gets a picture:

1. An administrator authors `artAssetId` on the Island (World) or Place (Location) content row.
   Authoring refuses an unknown id or a non-image kind (`apps/catalog/authoring.py`,
   `ART_ASSET_KINDS = ("image",)`).
2. The islands API sends it as `thumbnailAssetId` only when that id is an **active image whose
   default version is published** (`apps/game_sessions/discovery.py` `published_art`); otherwise
   `null`.
3. The card's `RealmPicture` resolves it through the child-scoped Django asset resolver
   (`react/src/features/realms/imageResolver.ts`, ADR-030, LAI-2200): ids asked for in one tick
   go out as one request, and anything but a published image is `null`.
4. The drawn scene (`RealmIllustration`, picked per slug by `realmThemes.ts`) always renders; a
   published image loads lazily on top and is dropped on a load error, so a child never sees a
   broken image.

| Realm card (#104) | Slug | Authored `artAssetId` on `main` | Published thumbnail | What the child sees | Fallback scene |
|---|---|---|---|---|---|
| Treasure Rush | `pirate-builder-bay` (Place, when its Area is `treasure-rush-cove`) | None | No | Drawn illustration | `treasure` (ship, palms, treasure) |
| Storykeeper's Castle | `storykeeper-castle` (Place) | None | No | Drawn illustration | `castle` |
| Heart of Firepeak | `firepeak-volcano` (Place) | None | No | Drawn illustration | `volcano` |
| North Pole | `north-pole` (Realm) | None | No | Drawn illustration | `winter` |

Findings:

- **The integration is correct and uses only the existing Asset Library and delivery path.** PR
  #104 reuses `RealmPicture` and `ImageResolverProvider` unchanged, hard-codes no image URL and
  bundles no reference artwork. Its own realm tests on `2d8db97c`: see section 5.
- **No realm has a published thumbnail today, and no approved artwork exists to publish.** The
  only realm-named PNGs in git are QA screenshots (`docs/qa/npc-manager/*.png`), which are not
  artwork. Every card therefore shows its drawn scene, which is the designed fallback, not a
  defect.
- **To add one** (an owner decision; needs licensed or original art): upload the image as an
  `image` asset in Django Admin, publish it, then set `artAssetId` on the Place or Realm
  revision. No code change is needed, and the card switches on the child's next load.
  Unpublishing or retiring the image returns the drawn scene at once.

## 3. Other realms: do assets cause #98, #99 or #100?

**No.** Each fails before any asset is resolved. Assets that cannot be delivered never block a
3D Area: the resolver falls back to the bundled model, then to a placeholder or stand-in. The one
asset step that can block is client manifest validation (`UNKNOWN_ASSET`).

| Issue | Asset-related? | Cause seen (owner of the fix) |
|---|---|---|
| #98 North Pole, "We could not find that island" | No | Client routing: `getWorld('north-pole')` is undefined because `react/src/features/worlds/worlds.ts` registers only the home island and Creature Care Cove (LAI 03, confirmed independently) |
| #99 Storykeeper's Castle cannot be entered | No | No Django `WorldRegion` for the castle (it is a bundled TypeScript layout), so the Realm and Place UI offer no 3D link (LAI 02 reproducing) |
| #100 Firepeak cannot be entered | No | Its regions are puzzle-only with no chest, so `area.available` (chest with a published challenge) is false and the card has no entry; Pathfinder/Explorer only; DRAFT until `publish_firepeak*` (LAI 03 reproducing) |

**Asset defect found and fixed (section 4): North Pole would have failed next.** Its scene names
`north-pole-snowy-pine`, `north-pole-lantern` and `north-pole-candy-cane` only in
`layout.scenery`. The region catalog the play API sends did not read `layout.scenery`, the client
validates every scenery id against its bundled manifest plus that catalog, and none of the three
is bundled. Once #98's routing is fixed, the served North Pole Area would have been refused with
`UNKNOWN_ASSET`. The Vitest fixture hid this by adding the scenery ids to its catalog itself
(`react/src/test/northPoleFixtures.ts`).

## 4. Fix: the region catalog names every scene asset

`apps/game_sessions/play_state.py` `region_catalog` now collects scene ids with the dependency
registry's own walk (`apps.regions.dependencies.scene_asset_ids`: `assetId`, any `...AssetId`,
any `...AssetIds` list) instead of a hand-picked set of layout keys. One rule now decides both
what retirement protects in a scene and what the client is told about, so scenery, platform and
building ids cannot drift apart again. Behaviour is otherwise unchanged: only ids with a
`ContentAsset` row are listed, with the same `kind`, `clips` and `deliverable` fields.

Regression tests (`apps/game_sessions/tests/test_environment_catalog.py`):

- North Pole's scenery-only ids are in the catalog (fails on `main`).
- For the seeded Treasure Rush and North Pole regions, every scene id the dependency registry sees
  that has a definition is in the catalog.
- Scenery, platform, building and `...AssetIds` ids are listed; an id with no definition is not.

`apps/game_sessions/tests/test_region_catalog_completeness.py` applies the client's rule on the
server: every asset id a served Area names (scene, objects, NPCs) must be bundled
(`content/exported/assets.json`) or in the catalog it is sent with.

- North Pole Village served through the play API to a Sprout, a Pathfinder and an Explorer: no
  unknown asset, and the three scenery ids are listed.
- Firepeak Volcano and Heart of Firepeak (seeded): no unknown asset.

On `main` the four catalog tests above fail and pass with the fix. Treasure Cove was not affected:
the ids the old catalog skipped there (its `scenery` and `ambient` entries) are all bundled, so the
client already knew them.
